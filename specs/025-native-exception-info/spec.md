# Native Exception Information

Status: source integrated via PR #394 at `9732184ecf8af20944deacad5e3421def3a287f7` after controlled DAP checks; a real debugger and installed delivery remain pending. This additive source slice started from `c5473501b9fc5b8e763f5a94f4ef5c32cf047fee`; Python remains the installed default and rollback. It does not establish complete Python parity or completion of the migration.

## Consumer outcome

A native MCP client examining a stopped thread can retrieve the debugger's exception identity, break mode, description and nested details when the adapter advertises DAP exception-info support. The returned information is an observation of that stopped thread, not proof that a later stop refers to the same exception.

## Contract

- Add `get_exception_info(debugSessionId, threadId)` to the existing stateful host. Both inputs are required: a nonblank opaque session ID and an explicit Int32 thread ID. Reject malformed or extra arguments before DAP I/O. Unknown or retired sessions use the existing not-found result. Unlike the Python tool, this slice does not infer the current thread, update Python's exception cache or provide the combined `get_exception_context` helper.
- Track `supportsExceptionInfoRequest` from the correlated initialize response and subsequent capabilities events in reader order. An absent or false capability refuses with a fixed `DAP_EXCEPTION_INFO_UNSUPPORTED` result without sending `exceptionInfo`. Do not infer support from adapter identity or fall back to another route.
- For an advertised capability and a currently inspectable stopped thread, send one DAP `exceptionInfo` request with the exact explicit `threadId`. Reuse the existing session admission gate, stopped-thread epoch and response-correlation owner; capability updates, lifecycle invalidation and actual write admission must not race into a request after an observed revocation. A stale target detected before writing, a negative adapter response, or a response invalidated before reader correlation returns a fixed `DAP_EXCEPTION_INFO_REFUSED` without returning stale exception data. A later capability change alone does not invalidate a reply to an already admitted request while its stopped-thread epoch remains current. No automatic retry is performed.
- On a current successful response, return `kind: exception_info_success` with an `exception` object preserving the adapter's response body, including nested details and extension fields. The body must be an object with string `exceptionId` and a valid DAP `breakMode` (`never`, `always`, `unhandled`, or `userUnhandled`); if present, `description` must be a string and `details` an object. Apply the existing 256 KiB complete serialized inspection-content limit and identical structured/text content. Do not silently truncate the exception body.
- Malformed or oversized responses, timeouts and protocol failures return fixed redacted `DAP_EXCEPTION_INFO_PROTOCOL_ERROR` and use the existing lease-release-before-close-and-drain owner. Cancellation before writer handoff preserves the session; a potentially partial DAP frame invalidates inspection and drains. A fully committed read-only request does not claim a debuggee mutation merely because its caller stopped waiting. Explicit stop and host disposal retain the existing lease/grace/abort semantics.
- Do not alter Python, preview publication, UI input, default selection or release state. Python's implicit thread selection, cached state/resource updates and combined exception autopsy remain separate migration obligations.

First add a test-only public discovery regression and observe it fail on the base; then implement and rerun the same path. Cover true/false/absent and updated capability, exact thread request and complete body, invalid/unknown/stale admission, DAP refusal, malformed/oversized body, and reader-ordered invalidation. Extend existing tests and fixtures only; do not create a new verification harness or test suite.
