# Native UI Main-Window Discovery

Status: implemented; verification and integration pending. Baseline: `326d8d8e53a45eadd80b9a5920ed986241b76819`. Parent outcome: a consumer-proven .NET replacement; the installed Python route remains the default and rollback. This slice does not complete that outcome or change the published read-only preview.

## Caller outcome

A client with an existing native `debugSessionId` can inspect the bound debuggee's current main window, discover an AutomationId that was not known beforehand, and invoke the intended control once. Discovery is read-only. It does not activate the window, move focus, send input, expand controls, or resume the debuggee.

The native catalog currently has `ui_invoke` but no ordinary window-tree or element-discovery tool. A source-built MCP `tools/list` consumer observed this gap at the preceding source revision; the baseline is retained at `.agent/runs/python-removal-strangler-program-v1/first-native-journey/native-ui-discovery-baseline.json`.

## Contract

- Add `ui_get_window_tree` for the session's current main window only. Require `debugSessionId`; accept optional integer `maxDepth` from 0 through 32 (default 3) and `maxChildren` from 1 through 256 (default 50). Reject null, malformed, extra, fractional, boolean, and out-of-range arguments before starting a helper.
- Return a complete MCP result with matching JSON text and `structuredContent`. Identify the scope as `main_window` and atomicity as `unproven`; include the observed process incarnation, main-window identity, and a parent-first bounded tree. Each node carries a response-local node ID, parent ID, exact AutomationId when readable and within 256 Unicode code points, display name, control type, opaque runtime ID, observed InvokePattern support, and explicit unreadable/truncated field and child-completeness information. Never return a shortened AutomationId as an actionable selector. Duplicate IDs remain separate observations.

  The response shape is `kind: ui_window_tree`, `scope: main_window`,
  `atomicity: unproven`, `process: {processId, processIdentity}`,
  `window: {hwnd, runtimeId}`, `nodes`, `limits: {maxDepth, maxChildren,
  maxNodes}`, and `truncated`. Nodes use `nodeId` (zero-based preorder),
  `parentId` (null for the root), `automationId`, `name`, `controlType`,
  `runtimeId`, `supportsInvoke`, `childrenComplete`, `unavailableFields`, and
  `truncatedFields`. Unsupported values are null with an explicit reason.
  `hwnd` is an opaque, lossless string that the caller only echoes.
- Report depth or per-parent truncation explicitly. A partial tree cannot establish that an element is absent or unique. Bound traversal to 4,096 nodes, the observation request to 8,192 bytes, the helper response to 262,144 bytes, and the final serialized MCP response, including its text mirror, to 1,048,576 bytes. Do not materialize an unbounded child collection before applying the bound.
- Add an optional closed `expectedTarget` object to `ui_invoke`, containing the observed process identity, main-window handle represented losslessly as an opaque string, root runtime ID, and element runtime ID. All fields are required when supplied; runtime IDs are arrays of 1–64 Int32 values. These values are comparison constraints, not authority to choose another process or window. Mismatch refuses with `UI_INVOKE_TARGET_CHANGED` and `outcome: not_invoked`. Existing two-argument `ui_invoke` callers keep their current behavior and response shapes.

  The exact expectation fields are `processIdentity`, `hwnd`, `rootRuntimeId`,
  and `elementRuntimeId`. The caller obtains them from one discovery response;
  they do not expose a new target-selection operation.
- The `expectedTarget` form of `ui_invoke` keeps a strict bounded exact-AutomationId search. It must not act if any relevant ID cannot be read or the bounded traversal is incomplete. Two known equal IDs establish ambiguity even if another ID is unknown. Existing two-argument calls retain their previous selection behavior, including treatment of unrelated unsupported or overlong IDs.
- Add the separate `ui_invoke_observed` tool for an explicitly observed element. It requires exactly `debugSessionId`, `target`, and `expectedAutomationId`; `target` is the same closed four-field object as `expectedTarget` above. The expected ID must be readable, exact, nonempty and within the existing 256-code-point selector limit. It checks the selected element's ID; it does not assert that the ID is globally unique. No call automatically falls back between the two tools.
- For `ui_invoke_observed`, traverse the bounded raw main-window tree and require exactly one element with the requested runtime ID. An unreadable process or runtime identity, incomplete traversal, or duplicate of the requested runtime ID refuses without acting. Validate the selected element's exact AutomationId, process, main HWND, root identity, and InvokePattern. Repeat resolution and validation at commit, then invoke at most once. Unknown or duplicate AutomationIds on other elements are not evidence of their absence and do not select the target. A success reports `kind: ui_invoke_observed_success`, `selection: runtime_id`, `invoked: true`, `method: InvokePattern`, and `atomicity: unproven`; an uncertain post-commit outcome is never reported as not invoked or retried automatically.
- Malformed arguments and absent sessions retain the host's existing `invalid_tool_arguments` and `debug_session_not_found` shapes. Action `tool_error` results from `ui_invoke_observed` identify that tool, not `ui_invoke`: a refusal before commit reports `outcome: not_invoked`; a lost response or exception after a possible commit reports `outcome: unknown`, and unconfirmed cleanup preserves any known action outcome. Error messages describe runtime-ID selection rather than claiming an AutomationId-only search.
- Reuse the session registry, process-incarnation binding, main-window owner and single native UI helper lifecycle. Pin and recheck the process and HWND ownership around traversal, and recheck the live session before publishing. Discovery never scans or attaches to an unrelated process. Both action modes perform their own full bounded selection and prepare-to-commit identity recheck.
- Bound one discovery operation by a single 10-second deadline and owned helper cleanup by at most two further seconds. A stalled UIA provider must not block debugger state, continue, or stop. Cancellation, session retirement, and host shutdown close the operation and its owned helper; if cleanup cannot be confirmed, return a truthful error and do not admit another UI helper through that owner until cleanup is resolved. Do not claim a completed observation from a failed or incomplete ownership check.
- Distinguish invalid arguments and unavailable sessions from discovery unavailable, target unavailable/changed, busy, timeout/cancellation, unreadable observation, hard-limit overflow, and unconfirmed cleanup. An error is never a fabricated empty-success tree. Preserve existing `ui_invoke` not-invoked versus unknown-outcome behavior and never automatically retry an uncertain action.

## Boundaries and compatibility

Python's existing `ui_get_window_tree` covers all top-level process windows, and its selection/search behavior is broader. This native slice is explicitly main-window-only: it does not implement `ui_find_element`, selected-window state, sibling/modal-window actions, XPath, or full Python parity. The existing Python implementation and legacy clients remain unchanged. Later work must address those missing journeys before default cutover or Python retirement.

UI Automation runtime IDs are opaque comparison values and may be reused over time. An `expectedTarget` or observed target detects observable drift; neither is a durable element lease or proof of unchanged business meaning. UI Automation supplies no atomic compare-and-invoke transaction here: a replacement that preserves all checked values may be indistinguishable. A successful invoke means only that InvokePattern returned, not that the application's handler completed.

## Verification and integration

1. Retain the pre-implementation RED regressions for the missing public discovery route and guarded discovery-to-invoke behavior. Preserve the observed unreadable-ID failure: strict `ui_invoke` must refuse without action when another ID is unknown. Add test-first coverage for explicit runtime-identity selection, including duplicate and unreadable IDs on other nodes, unreadable or duplicate runtime IDs, changed target/ID, no action on refusal, and existing two-argument behavior with unrelated overlong IDs. Also cover wrong process/window, input/size bounds, cancellation, blocked UIA, retirement, and owned helper cleanup. Preserve Python UI tests.
2. Implement one coherent slice through the existing MCP registry, bound session, native UI helper owner and FlaUI bridge. Keep observation IPC read-only and distinct from the invoke commit; strict, legacy, and observed-element selection remain explicit. Update the existing application schema, README and changelog with the explicit native boundary and runtime-ID limitations.
3. Exercise a source-built candidate through a fresh official MCP client, real netcoredbg, and the existing WPF smoke app. The fixture generates an AutomationId at startup without disclosing it through another channel. Discover it by label/type, add a breakpoint, issue `ui_invoke_observed` exactly once with the observed target and ID, inspect the real stop and continue, then verify a visible application action counter through a later tree read and explicitly clean up. WPF may complete InvokePattern before or after the handler reaches the breakpoint; neither ordering is assumed. `continue_execution` remains a long-poll operation, so observe continuation and application state independently rather than requiring its response within the UI helper deadline.

   For the real WPF smoke fixture, the new button's visible name is `Native
   discovery action`; its runtime-generated AutomationId is not returned except
   by discovery. A separate visible status reports `Native discovery count: N`.
   The consumer finds the button by name/type and does not construct its ID.
4. Separately use a controlled blocked-helper case to prove debugger operations remain responsive during a truly pending UIA operation. Preserve exact failures and unknown outcomes; do not substitute that controlled case for the real-debugger journey.
5. Independently review the exact implementation and perform affected regression checks. This source slice is not installed delivery, full parity, release readiness, or Python removal.

Design evidence: `agent://NativeUiDiscoveryDesign`; independent challenge: `agent://UiDiscoveryChallenge`. A controlled WPF observation in `.agent/runs/python-removal-strangler-program-v1/first-native-journey/ui-automation-unsupported-probe.log` showed that UIA exposed the same unsupported sentinel for a normal system menu item and an element whose ID getter failed. The original strict-ID WPF success criterion is therefore replaced by the explicit observed-element route above; strict `ui_invoke` remains fail-closed and is tested separately. This is a technical selection-contract change, not proof of global AutomationId uniqueness. The consumer oracle follows WPF's [asynchronous ButtonAutomationPeer implementation](https://github.com/dotnet/wpf/blob/v8.0.0/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Automation/Peers/ButtonAutomationPeer.cs#L51-L62).
