# Native DAP step-over

## Outcome

An opt-in modern native MCP client with a live opaque debug session and an explicitly named currently-authorized stopped Int32 thread can call `step_over(debugSessionId, threadId)`. Per `NetCoreDbgSession`, one fail-fast private single-flight record permits one admitted call; a concurrent call receives typed refusal with zero DAP I/O. The admitted native session sends only correlated DAP `next({threadId})`, accepts its exact positive acknowledgement, and within one 30-second post-write wall-clock limit returns only an exact later `reason:"step"` stop for that same explicit thread, a typed terminal result, a typed timeout result, a typed refusal, or a redacted protocol error. The installed Python route remains selected default/rollback and is not called or changed.

## Protocol evidence

`docs/dap-protocol/specification.md` §§1824–1870 and `docs/dap-protocol/debugAdapterProtocol.json` definitions `NextRequest`, `NextArguments`, and `NextResponse` establish that `next` has required Int32 `threadId`, optional `singleThread` and `granularity`, acknowledgement-only response, and response-before-`stopped(reason:"step")` order. The same vendored schema defines stopped execution/event fields at lines 189–241 and notes that `continued` may be omitted for a request implying continuation at lines 243–270. The specification does not guarantee equality between the requested `threadId` and a subsequent stopped event’s optional `threadId`; B3 therefore makes exact observed equality a native success condition rather than assuming it.

## Requirements

- **B3-REQ-001 — Closed explicit public input:** `step_over` accepts exactly `{debugSessionId,threadId}`. Both fields are required. `debugSessionId` is a non-whitespace string; `threadId` is an Int32. Missing arguments, omitted fields, empty/whitespace or non-string token, non-integral/out-of-range thread number, and any extra field return existing `invalid_tool_arguments` for tool `step_over` before DAP I/O. No optional thread, current thread, first thread, frame, target, source, `singleThread`, or granularity exists at this boundary.
- **B3-REQ-002 — Opaque token and narrow DAP authority:** The registry resolves only a currently live opaque native `debugSessionId`. Any unavailable non-whitespace token returns existing `DEBUG_SESSION_NOT_FOUND` with zero DAP I/O and no token grammar disclosure. The only B3 adapter request is internal typed `next` with exactly `{threadId}`; B3 never sends optional `singleThread` or `granularity`, does not infer `supportsSingleThreadExecutionRequests`, and does not forward generic DAP commands.
- **B3-REQ-003 — Atomic admission, single-flight, and invalidation:** With the existing `SessionSlot` lease held, `NetCoreDbgSession` takes the existing `_callStackAdmissionGate` and `_stateGate` together in established order to require capability-independent current stopped authority for the supplied thread and reserve its one nullable active B3 record. An occupied record returns `dap_step_over_refused` with zero DAP I/O. The admitted record has only private identity, target, positive-acknowledgement state, possible-write and full-commit states, absolute deadline, and completion signals. Admission clears every stopped-authority and B2 call-stack/frame-authority token, registers the correlated pending `next`, and writes before releasing admission. Absent current authority causes refusal with no write. The record is not a public cache, registry, selector, queue, generic execution framework, or exclusive `SessionSlot` mode.
- **B3-REQ-004 — Correlated acknowledgement and exact later observation:** The operation accepts only a positive response whose request sequence and command equal its registered `next`. Only a later reader `stopped` event with `reason:"step"` and an Int32 `threadId` exactly equal to the supplied target returns `{kind:"step_over_success",threadId}`. Every stopped event before acknowledgement, with a missing/different thread id, or with another reason updates normal session lifecycle/authority but is ignored by the B3 waiter; `allThreadsStopped:true` never substitutes for the exact causal target match. `exited` or `terminated` may settle the active record before or after acknowledgement. The public contract has only the five outcomes in B3-REQ-006 and no additional event-rejection branch.
- **B3-REQ-005 — Capability-independent stopped authority and ordering:** One event-owned stopped-thread authority is separate from B2’s delayed-stack capability: `allThreadsStopped:true` creates an all-target epoch; otherwise an explicit stopped Int32 `threadId` grants only that target; a stop missing both grants none. Existing continued and terminal handlers invalidate authority through the established admission/state serialization. B2 paging continues to require both current authority and explicit `supportsDelayedStackTraceLoading`; B3 admission requires authority only. Admitted `next` is an immediate continuation boundary because the DAP schema permits its `continued` event to be omitted: it clears all authority before the write, and a later `continued` keeps it invalid.
- **B3-REQ-006 — Bounded typed outcomes:** One absolute 30-second deadline begins only after the admitted `next` header, complete payload, and flush have all completed, not at admission or the possible-write marker. It covers exact acknowledgement plus later observation using the same remaining budget. The closed outcomes are `step_over_success` (not error), `step_over_terminal` with `terminal:"exited"|"terminated"` and optional recorded Int32 `exitCode` (not error), `step_over_timed_out` with `threadId` and `timeoutSeconds:30` (not error), `dap_step_over_refused`, and `dap_step_over_protocol_error` (errors). Each application result is complete: normalized `structuredContent` and one text item containing its identical JSON serialization. No result exposes raw DAP body/message/event, adapter exception text, raw stack/frame/source values, retry details, or token internals.
- **B3-REQ-007 — Protocol failures and uncertain-act cleanup (revised):** Wrong command/correlation for the active pending sequence, malformed active response, non-boolean `success`, DAP framing/read/write failure, reader failure, or unexpected internal failure maps to exactly `{kind:"dap_step_over_protocol_error",error:"DAP_STEP_OVER_PROTOCOL_ERROR"}` and no partial success. A negative acknowledgement preserves the usable session. Caller cancellation completed before writer handoff, with no initiated or late `next` write, clears pending/active records and retains the same token, slot, and adapter; admission-invalidated stopped/B2 authority is not restored. After opaque writer entry or possible, partial, or unknown transmission, caller cancellation propagates only after releasing the operation lease and joining existing `SessionSlot.CloseAndDrainAsync`; later access is `DEBUG_SESSION_NOT_FOUND`, including fixture-known zero-byte delivery. Cancellation between the final token check and `WriteAsync` may conservatively drain; there is no physical-first-byte atomicity guarantee. Post-commit timeout takes the same release-before-drain path. `SessionSlot` alone owns token removal, abort, one-winner drain, stop, and dispose.
- **B3-REQ-008 — Scope and compatibility:** B3 is an additive modern-native tool after `get_call_stack`. It does not alter existing tools, B1/B2 public outcomes, Python behavior, package/default selection, persisted data, UI/bridge, release, or publication. B2 provenance is binding: its feature merged to `main` at `eb84c55`; B3 does not claim that merge’s historical tests as current B3 evidence. ## Scenarios

1. A live opaque token, explicitly supplied current-authority Int32 target, and controlled adapter sequence `stopped -> next acknowledgement -> stopped(reason:"step", same threadId)` produce exactly one DAP `next` request containing only `threadId`, `step_over_success`, one JSON-identical text item, and a session that `get_debug_state` can still query.
2. Missing arguments, either required field, a whitespace/non-string token, non-Int32 thread, or an extra field returns `invalid_tool_arguments` for `step_over` and zero DAP writes. A syntactically valid unavailable opaque token returns `DEBUG_SESSION_NOT_FOUND` and zero DAP writes.
3. A session without current stopped authority for the exact target returns `DAP_STEP_OVER_REFUSED` with zero `next` writes. A second concurrent `step_over` while the session-private active record is occupied returns the same refusal and zero DAP writes. A negative correlated `next` acknowledgement returns refusal without raw adapter diagnostics and retains session usability.
4. A stopped event with `allThreadsStopped:true` authorizes each target without a delayed-stack capability; a partial event authorizes only its supplied target, and one missing both all-stop and thread grants none. B2 `get_call_stack` remains capability-gated while B3 is not. Step admission clears B2 frame and stopped authority before its `next` write. A controlled held-write/continued race proves the reader cannot restore old authority before admission completes; a `get_call_stack` request for old authority cannot publish stale frames between step admission/continued and a fresh stopped event.
5. Pre-acknowledgement stopped events and later events with an omitted/different thread id or non-step reason each update ordinary lifecycle but are ignored by the B3 waiter and never report success. A later exact post-acknowledgement `stopped(reason:"step",same target)` still succeeds. If no exact event or terminal follows, the shared deadline produces timeout and closes/drains the session; no raw stopped payload is returned.
6. `exited` or `terminated` before or after acknowledgement returns `step_over_terminal` with only the normalized terminal discriminator and an optional already-recorded Int32 exit code. No later stale stopped event can convert it to success.
7. No exact observation before the one 30-second deadline, started after complete header/payload/flush commit, returns `step_over_timed_out` with `timeoutSeconds:30`, then close/drain and later `DEBUG_SESSION_NOT_FOUND`. Proved pre-writer cancellation retains the same token/slot/adapter, clears pending/active records, restores no stopped/B2 authority, and emits no late `next` after its barrier is released. A separate test-owned correlated `get_threads` must succeed through that retained registry before cleanup; a cached state query alone is insufficient. After writer entry, zero-byte, partial-header, unknown-write, and final-token-check/entry cancellation cases require completed release-before-drain before propagation and later not-found. B3 itself performs no retry, auto-pause, auto-continue, `get_threads`, or stack/source read.
8. Wrong command/correlation for the active pending request, malformed success, reader failure, write failure, or other malformed DAP exchange returns exactly `DAP_STEP_OVER_PROTOCOL_ERROR`, no partial outcome, then existing close/drain behavior and `DEBUG_SESSION_NOT_FOUND` for later access.
9. On the exact candidate, each named native process/typed-session/lifecycle/schema baseline in B3-REQ-009 reports an actual nonzero denominator and is recorded in `.agent/runs/b3-native-step-over/receipt.yaml`. The retained installed-Python journey continues to reach `PRODUCT_WORKS` as a non-selection proof; B3 does not invoke the Python implementation.
